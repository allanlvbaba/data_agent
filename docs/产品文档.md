## 1. 产品概述

### 1.1 一句话定位

**掌柜问数**是一个面向业务人员(掌柜/运营/老板)的**对话式数据问答助手(ChatBI)**:用户用一句中文提问,系统在数秒到一分钟内自动完成"理解 → 检索 → 生成 SQL → 执行 → 表格呈现"的全过程,全程不需要用户会写 SQL。

### 1.2 要解决的业务问题

| 传统取数模式 | 痛点 | 本产品的解法 | 对应能力 |
|--------------|------|--------------|----------|
| 业务提需求 → 数据同学写 SQL | 需求排队,交付以天计 | 自然语言直问,单轮闭环 | F1 问数主链路 |
| 固定报表看板 | 维护贵、维度不灵活 | 即席任意维度组合查询 | F1 + F5 元数据驱动 |
| 指标口径靠口口相传 | 数字对不上,信任崩塌 | **指标语义层**:GMV/AOV 的口径在知识库中唯一定义,LLM 被约束"不得重解释" | F4 指标治理 |
| 黑盒工具不敢用 | 不知道答案怎么来的 | 前端实时展示"抽取关键词→召回→筛选→生成SQL→执行"每一步 | F2 过程可视化 |

### 1.3 产品原则(从架构反推的设计观)

1. **先宽后严**:召回阶段"宁多勿漏"(向量+全文三路宽召回),筛选阶段"宁缺毋滥"(LLM 按最小必要集合裁剪)——保住召回率的同时控制上下文长度与 SQL 正确率。
2. **知识库驱动,代码零改动扩展**:新增一张表、一个字段、一个指标,只需要编辑 `conf/meta_config.yaml` 并重跑构建脚本,**不写一行代码**(见 §6)。
3. **过程透明**:每一个阶段都通过 SSE 推送到前端(用户看到的是流程步骤条,而非无限转圈)。
4. **口径即约束**:指标一旦定义,生成 SQL 的提示词中被硬性要求"严格遵循业务口径,不得偏离或重解释"(见 `prompts/generate_sql.prompt` 任务要求第 2 条)。

## 2. 用户与场景

### 2.1 用户画像

| 画像 | 特征 | 高频诉求 | JTBD(待办任务) |

### 2.2 典型场景(可直接验收)

| 场景 | 示例问题 | 系统需要命中的要素 |
|------|----------|---------------------|

## 3. 市场与差异化

### 3.1 赛道速览

ChatBI/NL2SQL 是 BI 智能化的主流方向(国际:Tableau/ThoughtSpot 的 AI 问答;国内:各 BI 厂商 ChatBI)。通用方案通常两条路线:**直连大模型一把生成 SQL**(简单但幻觉率高、schema 超长不可控)或**语义层全预定义**(可控但灵活度差)。

### 3.2 本产品的差异化设计

| 差异点 | 通用直连方案 | 本产品做法 | 产品价值 |
|--------|--------------|------------|----------|
| Schema 注入方式 | 全库 DDL 塞进 prompt(表多即爆炸) | **召回-筛选两段式**:只注入与问题相关的 2~3 张表及其字段 | 上下文短 → 便宜、快、准 |
| 业务词映射 | 靠 prompt 硬猜 | 字段/指标**别名+描述+示例值**三重语义入知识库("销售额/收入/成交总额"都指向 `fact_order.order_amount`) | 口语可命中,口径可治理 |
| 短枚举值 | 向量检索丢"Q1"这类短值 | ES + IK 分词的**字段值全文召回**补盲区 | 枚举过滤类问题可用 |
| 结果可信度 | 黑盒 | 步骤条 + SQL 生成约束("仅允许使用真实存在的表与字段,禁止编造") + EXPLAIN 校验 + 失败自动修正 | 可解释、可兜底 |
| 部署 | 多为 SaaS | 全组件 Docker 化,LLM/Embedding 可替换为任意 OpenAI 兼容/本地服务,数据不出域 | 可私有化 |

## 4. 功能清单与用户故事

### F1 自然语言问数(核心)✅

- **用户故事**:作为运营,我想输入一句中文就得到数据表格,以便不排队等取数。
- **验收标准(AC)**:
  - AC1:对知识库内已登记的表/字段/指标,常见问法可返回正确结果表格(列名含中文别名);
  - AC2:问数过程在页面实时可见(≥6 个阶段节点);
  - AC3:生成的 SQL 只含查询语句,不含增删改;
  - AC4:生成失败或执行失败时,页面给出明确错误信息而非无响应。
- **实现锚点**:主链路 `app/agent/graph.py`(12 节点状态图);接口 `POST /api/query`(SSE)。

### F2 过程流式展示 ✅

- **用户故事**:作为老板,我想看到系统"正在做什么",以便相信这个结果是可信的。
- **AC**:每个阶段以"步骤点"呈现(黄点执行中/绿点完成/红点失败);后端每阶段通过 `runtime.stream_writer` 推送 `{"stage": "..."}`(见各节点第一行代码),前端 `App.vue` 按 SSE 事件驱动步骤条状态机。
- **产品意义**:可解释性 = 信任感;同时是 badcase 定位的天然埋点。

### F3 结构化结果表格 ✅

- **AC**:结果自动识别列(取第一行 key,含中文别名,如"品类/销售额/销售额占比");支持横向滚动;空结果有明确提示。
- **实现锚点**:`App.vue` `data.result` 分支。

### F4 指标语义层 ✅

- **用户故事**:作为数据负责人,我想让"销售额""成交总额""收入"都算同一个口径,以便全公司数字一致。
- **AC**:指标在 `meta_config.yaml` 中唯一定义(name/description/relevant_columns/alias);召回命中后由 `filter_metric_info` 判定是否真正参与本次回答;生成 SQL 时被强约束遵循口径。
- **佐证(真实日志)**:问题含"销售额",召回命中 `GMV/AOV` 两个候选,筛选后仅保留 `GMV`(最小集合原则)。

### F5 元数据驱动扩展 ✅

- **AC**:新增表/字段/指标 = 改 `meta_config.yaml` + 重跑 `build_meta_knowledge`,不改代码;`sync: true` 决定该字段值是否进入全文检索(维度值少的适合 true,如季度;事实表度量默认 false)。
- **产品含义**:知识库运营成本 ≈ 写一段中文描述,业务人员可参与共建。

### F6 SQL 自动纠错 ✅

- **AC**:`EXPLAIN` 校验失败时,携带**原始 SQL + 数据库报错信息 + 上下文**让 LLM 做"最小必要修复",修复后重新校验执行,用户无感知。
- **实现锚点**:`validate_sql` → 条件边 → `correct_sql`(提示词 `prompts/correct_sql.prompt`,9 条修复纪律:只修错误、不改语义、最小改动)。

### 规划中

| 编号 | 功能 | 一句话说明 |
|------|------|------------|
| F7 | 多轮追问 | "那再按省份拆一下"——依赖会话内 state 继承 |

## 5. 端到端体验与真实时延剖析

一次真实提问的**分阶段耗时**(来自 2026-10-03 运行日志,CPU 版 Embedding 服务):

| 阶段 | 开始时刻 | 耗时 | 用户看到 |
|------|----------|------|----------|
| 抽取关键词 | 19:33:24 | <1s | 步骤 1 变绿 |
| 三路召回(并行) | 19:33:24 | **~41s** | 步骤 2~4 |
| 合并召回信息 | 19:34:44 | <1s | 步骤 5 |
| 筛选指标/表(并行) | 19:34:44 | ~19s | 步骤 6~7 |
| 添加上下文 | 19:35:03 | <1s | 步骤 8 |
| 生成 SQL | 19:35:03 | ~9s | 步骤 9 |
| 校验+执行 | 19:35:12 | ~0.1s | 步骤 10 + 表格 |
| **合计** | — | **约 108s** | — |

**产品视角的解读**:
- 瓶颈在**召回阶段逐关键词串行调用 CPU 向量服务**(每个关键词 1~3 秒 × N 个关键词);生产环境换 GPU Embedding 或批量/并发调用后,端到端可压缩到 10 秒级(优化项已列入开发文档 §11)。
- 正因为单轮耗时长,**过程可视化(F2)不是锦上添花,而是留存关键**——用户看到步骤在推进,才愿意等。

## 6. 知识库运营手册(业务同学可操作)

知识库的唯一编辑入口是 `data-agent/conf/meta_config.yaml`,三段式结构:

```yaml
tables:                      # 表级:name / role(fact|dim) / description
  - name: fact_order
    role: fact
    description: 订单事实表,记录订单数量和金额等核心指标。
    columns:                 # 字段级:name / role / description / alias / sync
      - name: order_amount
        role: measure        # primary_key | foreign_key | dimension | measure
        description: 订单金额。
        alias: [ 销售额, 订单金额, 收入 ]   # 口语词命中靠这里
        sync: false          # 是否把该字段的取值同步进全文检索
metrics:                     # 指标级:口径治理的载体
  - name: GMV
    description: 全称Gross Merchandise Value,表示所有订单的成交金额总和。
    relevant_columns: [ fact_order.order_amount ]
    alias: [ 成交总额, 订单总额 ]
```

**编辑规范(产品侧约定)**:

| 字段 | 规范 | 为什么 |
|------|------|--------|
| description | 一句话业务语义,写"给AI看的话" | 字段的 description 会作为向量入库的**独立文本**,描述质量直接决定召回率 |
| alias | 口语同义词,尽量全 | 别名同样独立向量化,是"人话→字段"的桥梁 |
| role | 严格按主键/外键/维度/度量 | 合并阶段会**自动补齐主外键**(保证 JOIN 可用),度量/维度影响 LLM 用法 |
| sync | 枚举值少且常被过滤的维度字段设 true | sync=true 会把该列全部取值(上限 10 万行)灌入 ES |
| 指标 description | **必须写清计算口径与时间口径** | 生成 SQL 时 LLM 被要求"严格遵循,不得重解释" |

变更后执行 `uv run python -m app.scripts.build_meta_knowledge -c ./conf/meta_config.yaml` 生效。

## 7. 质量与评估体系

### 7.1 Badcase 分类树(定位到阶段即可定位到责任人/文件)

| 现象 | 归因阶段 | 排查入口 |
|------|----------|----------|
| 该召回的字段没召回 | ① 关键词 / ② 召回 | 日志"关键词提取"清单;`prompts/extend_keywords_for_*.prompt`;Qdrant/ES 阈值(0.6)与 topK(5) |
| 召回了但筛掉了 | ④ 筛选 | `prompts/filter_table_info.prompt` 的"最小必要集合"规则是否过严 |
| SQL 语法/表列错 | ⑥ 生成 | `prompts/generate_sql.prompt`;筛选后注入的 schema 是否完整 |
| 数字口径不对 | ⑥ 生成 / 指标定义 | 指标 description 是否写清口径;LLM 是否违规重解释 |
| 执行报错但没自动修复 | ⑦ 修正 | 已知问题:修正节点回流缺失(见开发文档 §12 P0-1) |

### 7.2 评估指标定义

| 指标 | 定义 | 当前基线 | 目标 |
|------|------|----------|------|
| 问数成功率 | 端到端返回非空结果且用户未标记错误的会话占比 | 待建评估集 | P1 ≥ 85% |
| SQL 执行成功率 | `EXPLAIN` + 执行通过(含一次修正)占比 | 演示集 100%(样本少) | ≥ 95% |
| 结果正确率 | 人工比对标准答案 | 待建设 | ≥ 90% |
| 端到端时延 | P50 / P95 | ~108s / 待测 | P1: ≤30s / ≤60s |
| 召回命中率 | 标注必需字段被召回的占比 | 待建设 | ≥ 95% |

### 7.3 评估集建设方法

从 `meta_config.yaml` 的表×字段×指标组合生成问题模板(时间/过滤/分组/占比/排序 5 类),每类 10 条,人工标注期望 SQL 与期望结果行;每次改提示词/换模型全量回归。

## 10. 产品 FAQ

**Q1:为什么有时召回了一堆表最后只留下 2~3 张?**
召回按"宁多勿漏"宽松取(topK=5/词,阈值 0.6),筛选按"最小必要集合"裁剪——这是设计行为,不是 bug。

**Q2:换个问法答案的字段不一样?**
LLM 筛选与生成有随机性(temperature=0 已尽量压制)。关键差异请沉淀为别名/描述的改进,而不是换问法。

**Q3:"Q1"能被找到,靠的是什么?**
字段值全文召回:开启 `sync: true` 的维度字段的取值被灌入 ES,"Q1"精确命中 `dim_date.quarter`。

**Q4:可以接公司自己的大模型吗?**
可以。任何 OpenAI 兼容服务,改 `app_config.yaml` 的 `model_name/base_url` + `.env` 的 `APP_LLM_API_KEY` 即可。

**Q5:支持中文以外语言/其他数据库吗?**
当前面向中文与 MySQL 8 设计;多语言与多方言在 P2+ 规划。
